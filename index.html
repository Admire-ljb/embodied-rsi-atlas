首个 MCP 适配器

把时钟实验做成工具

软件组实现工具，AI 组在 Skill 中约定调用次序与判读方法。标准客户端通过 tools/list 发现工具及参数，通过 tools/call 调用。基线与新测结果均带运行号、事件标识和逻辑秒数。

读取基线

read_clock_reference(run_id)

从两次已发布的 AFSIM 实测中选择一条，返回该次实验的时钟标记和来源。

发起一次新测量

measure_clock_markers()

在本地启动一次固定的无实体时钟实验，生成新的运行号并返回实际输出。每次调用都使用同一份双标记输入。

查看调用示例与 kagent 绑定方式
{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"measure_clock_markers","arguments":{}}}

测量 Skill 先读取基线，再发起新测量，逐项对照标记和时间。kagent 的声明式 Agent 通过 mcpServer.toolNames 绑定这两个名称。集群接入需提供可达的 Streamable HTTP 服务，AgenticMesh 通过运行实例引用和调用标识关联证据。

官方 MCP 客户端已在 stdio 和 Streamable HTTP 上分别完成工具发现、读取基线与新测量。AFSIM 2.9.0 的两次新测均得到 1 秒和 3 秒的标记。GitHub Pages 提供代码、说明与实测记录。集群 Agent 调用、版本发布和半实物试验仍待联调。

递归验证

分别检验能力与改进器

一次任务得分提高，只能支持该能力版本在特定条件下有改善。要检验递归自我改进，还要追踪谁提出了改进器的新版本，以及新改进器是否更善于产生有效候选。

第一层 · 改进任务能力

以室内仪表巡检为例，旧观测摘要把“图像不清”写成了确定读数。进化面提出保留来源与“未知”的摘要候选。控制面在成对的留出记录上比较新旧版本，同时报告误报和可判读比例。

比较对象

同一任务和同一评价协议下的两版观测摘要。

第二层 · 改进产生候选的方法

若既有改进过程基于失败记录，提出改变候选样例的选择方式，则把此改动登记为改进器候选。让两版改进器从同一能力版本出发，在新批次享有相同预算，比较最终独立增益、波动和退化。

递归所需证据

改进器候选的产生来源、父版本，以及它在新任务批次中产生改进的能力。手工设计的候选只登记为对照。

当前公开内容包括架构设计、两份可校验的任务描述和实验模板。上述巡检过程是待验证的实验设计，实际运行和递归收益尚待研究。
